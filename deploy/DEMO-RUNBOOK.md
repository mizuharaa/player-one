# Thursday demo runbook — staff-assisted live demonstration

For the stakeholder meeting on **Thursday 2026-09-17**. This is the file the
room is run from.

It **supersedes steps 1–10 and the payment runbook of
[`centre/DEMO-SCRIPT.md`](centre/DEMO-SCRIPT.md)**, which was written for a
centre-PC-only walkthrough with no timing, no named owner per step and no
recovery. That file keeps the long-form
**[card procedure](centre/DEMO-SCRIPT.md#card-procedure-windows-ext4-tf-card--untested)**,
and this one does not repeat it — but read the next paragraph first, because
the measured card is not the card that procedure was written for.

**The card, measured (not inferred).** The real TF card is **exFAT**, label
`PlayerOne`, 240 GB. It automounts: a drive letter on Windows,
`/media/<user>/PlayerOne` on Linux. So **there is no WSL step, no `usbipd`
bind/attach, and no ext4 `ro,noload` mount** — the whole `usbipd`/ext4
procedure in `DEMO-SCRIPT.md` was written from documentation for an ext4 card
and does not apply to this one. It is kept there for the day a different card
appears, and it is still marked UNTESTED. What applies on Thursday: insert the
reader, let the card mount, and run the card-intake command (being written on
`lane/card-path`) against the session directory on the card. It copies with
checksums first and imports the copy. **The card is never written to and never
cleared** — CLAUDE.md rule 6, no exceptions, in no recovery path.

## T-60 minutes — preflight, before anybody is in the room

```bash
DATABASE_URL="postgres://playerone_app:...@<db host>:5432/po_demo_thursday" \
PLAYERONE_PUBLIC_URL="https://console.<domain>.vn" \
STORAGE_ENDPOINT=... STORAGE_BUCKET=... STORAGE_KEY=... STORAGE_SECRET=... \
PLAYERONE_BACKUP_DIR=/data/backups \
node deploy/demo-preflight.mjs
```

Every line must read `PASS`. It is read-only — SELECTs, one GET, one TLS
handshake, one HEAD, one directory stat — so it can be re-run as often as you
like, including during the demo.

A `FAIL` on `certificate-expiry`, `healthz` or `storage` is a **cloud-loss
decision point**, not something to fix at T-10. Go to
[Fallback A](#fallback-a--cloud-loss-the-centre-pc-variant).

If the database is empty, seed it once:

```bash
DATABASE_URL="postgres://playerone_app:...@<db host>:5432/po_demo_thursday" \
PLAYERONE_DEMO_MACHINE_SECRET=... PLAYERONE_DEMO_ADMIN_SECRET=... \
PLAYERONE_DEMO_FINANCE_SECRET=... PLAYERONE_DEMO_REVIEWER_SECRET=... \
node packages/api/scripts/seed-stakeholder.mjs
```

It refuses any database whose name does not start `po_demo` or
`playerone_demo`, it truncates nothing, and a second run adds nothing. Pass the
four secrets from the environment so a rerun is a rerun; omit them and it
generates and prints them once, and a later run with different values is
refused rather than overwriting a sign-in.

## The script — 35 minutes

Each row: the clock, who acts, what they do, the **state word** that must
appear, and what to do when it does not. The state words are the platform's
own (`batch_status`, `verification_state`, `review_state`,
`settlement_state`, and the app's `status`), not labels invented for the room.

### 0:00 — framing · narrator

Read "What is being claimed" above. No screen. **Recovery:** none needed; if
the room asks for the brief, `docs/` has it, do not improvise scope.

### 0:03 — card in, session declared · operator

Insert the reader; the exFAT card mounts by itself (a drive letter on Windows,
`/media/<user>/PlayerOne` on Linux). Run the card-intake command against the
session directory **on the card** — it checksums, copies, re-checksums, and
imports the copy, never the card. Do the copy before the room if the session is
large; the import is what the room watches. In the console: **Counter → new
handover**, pick the collector, the device and the card id, declare the
session.

**Expected:** a `handover_id` and a session on screen; the batch reads
**`importing`**. Say the batch id aloud.

**Recovery:** if the console refuses, the CLI is the same code path —
`node packages/api/bin/counter.ts import --session-dir <path>` (see
[RUNNING.md](../docs/RUNNING.md#the-operator-api)). If the resolver answers
**`operator_confirmation_required`**, that is the platform refusing to guess
between two handover-origin sessions: confirm the session on the `/episodes`
screen and say why it asked.

### 0:08 — upload and cloud verify · operator

The same `counter.ts import` call finishes the upload, or
`counter.ts upload --batch <id>` resumes one.

**Expected:** `cloud_verified: true` on stdout, the episode reads
**`verified`**, and there is one `cloud_verifications` row **per file, each with
its own sha256**. Read one hash aloud. Do not accept a run that only shows
`cloud_verified_at`: the proof is bytes re-read and re-hashed inside the VPC,
not an ETag.

**Recovery:** a failed verify leaves the batch resumable — re-run
`counter.ts upload --batch <id>`; it is idempotent and makes no second episode.
If the bucket itself is gone, go to
[Fallback A](#fallback-a--cloud-loss-the-centre-pc-variant). **The card is
never cleared, in any recovery, for any reason** (CLAUDE.md rule 6).

### 0:14 — the handset · collector-phone

On the phone: sign in with `+84900000001`, **Uploads → Tải lên → Chọn thư mục
phiên**, pick the session folder, upload.

**Expected:** the app reaches **`uploaded`** and the same episode appears in the
operator's console. The narrator says, here, that the six-digit code was filled
in by the demo account because ZNS is not issued yet — **staff-assisted, and a
real collector could not do this today.**

**Recovery:** [Fallback B](#fallback-b--handset-upload-failure-the-debug-delivery-page).

### 0:19 — human review · reviewer

The reviewer signs in on their own profile and opens `/review`, claims the
episode, and decides it.

**Expected:** the review reads **`pass`**, with `measured_duration_s` and
`effective_duration_s` both on screen. Read both aloud: the gap is the answer
to "why isn't the whole clip paid" — payable time is the *intersection* of
stream coverage, not the union.

**Honest line, said by the narrator at this step, not skipped:**

> The reviewer is seeing review metadata and no video. `PLAYERONE_REVIEWER_MEDIA`
> is `0` on this deployment, which means raw footage is never streamed to a
> remote reviewer session. PaXini's reviewers are in Shenzhen; whether video may
> leave Vietnam for them is a legal question that has not been answered, so the

**Recovery:** if the queue is empty, the episode is not eligible — a quarantined

`blocks_review` (two of the five real sample sessions carry `MEDIA-TRUNCATED`
and cannot be reviewed at all). Say which, from the `/episodes` screen, and
review the seeded episode instead. Do **not** flip
`PLAYERONE_REVIEWER_MEDIA=1` to "make review work": it is a different
authorisation, it requires `PLAYERONE_SECURE_COOKIES=1`, and nothing in this

### 0:24 — settlement and the bill · operator (NOT finance)

The verdict already wrote the settlement. The operator then runs the cycle:
`POST /api/settle/bills`, the `/settle` screen.

**Expected:** the settlement reads **`pending_settlement`** and then
**`bill_generated`**; a `bills` row with a `total` that is the exact sum of its
lines, never rounded.

**Recovery:** a refusal named `settle_generate_by_finance` means finance is
signed in on this screen — swap to the operator profile; that refusal is the
separation of duty working. A bill worth under one dong is refused as
`payout_attempts_amount_positive_check`; use the seeded bill.

### 0:28 — the payment, and the honest ending · finance

Finance opens `/settle/bills/<bill id>` and tries `POST
/api/payout/bills/:id/mark-paid` with the bill's whole-dong total.

**Expected — and this is the ending, not a failure:** the destination reads
**`unverified`**, and the call is refused by name
**`payout_attempts_account_unverified`**. The refusal comes from the database's
own trigger (`payout_attempts_guard`, migration `0012`, replayed in `0016`), not
from application logic that could drift from it. Nothing about the bill, the
settlement or the attempt state changes.

**The line the narrator says, verbatim:**

> This bill is correct and ready. It shows as **awaiting payment — destination
> unverified**. ZaloPay has not confirmed that this wallet belongs to this
> person, and the platform will not send money to an unconfirmed destination.
> That is a deliberate gate, not a missing feature. The moment VNG issues the
> ZaloPay verification credential, this same screen verifies the account and
> the same button records the payment.

**What changes if a verification credential does arrive before Thursday:** all
four of `PLAYERONE_ZALOPAY_APP_ID`, `PLAYERONE_ZALOPAY_PAYMENT_ID`,
`PLAYERONE_ZALOPAY_KEY1` and `PLAYERONE_ZALOPAY_PUBLIC_KEY` have to be present
— without all four no account can leave `unverified`. Then, and only then:

- Verification runs **on an isolated sandbox database**, never this demo
  database and never anything named live, with `PLAYERONE_ZALOPAY_ENV=sandbox`.
  A sandbox credential verifies sandbox wallets only.
- `PLAYERONE_PAYOUT_MODE` stays **`manual`**. A person sends the money and types
  the reference; the rail is not switched on for a demonstration.
- Re-run the preflight: `seed-payout` will read `verified` and say so, which is
  the signal to use the verified ending instead of this one.
- The verified ending is: finance retypes the exact whole-dong `amount_vnd` and
  the real transfer reference, `payout_attempts` records `amount_vnd`,
  `manual_reference` and `settled_at`, and the settlement reads
  **`manually_paid`**.

If no credential arrives, **do not simulate a payment.** A stubbed payment
shown to stakeholders is the one thing in this demo that would be a lie.

### 0:31 — the collector sees the same thing · collector-phone

## Fallback A — cloud loss: the centre-PC variant

Triggered by: `healthz`, `certificate-expiry` or `storage` failing the
preflight; the VM unreachable; or the GreenNode bucket refusing a HEAD.

**What the operator types.** The origin changes and nothing else does. On the
centre PC (`deploy/centre/README.md`):

```powershell
node deploy/centre/check.mjs preflight deploy/centre/centre.env   # must exit 0
.\deploy\centre\run-api.cmd
.\deploy\centre\run-caddy.cmd
node deploy/centre/check.mjs health deploy/centre/centre.env      # must exit 0
```

Then, on the LAN origin the centre PC serves (`PLAYERONE_PUBLIC_URL`, a private
IPv4 over plain HTTP, `PLAYERONE_SECURE_COOKIES=0`):

- **console and finance/reviewer profiles:** open that origin instead of the
  cloud hostname. Sign-ins are the same rows; the seed is per database, so the
  centre database needs its own `seed-stakeholder.mjs` run.
- **the handset:** the app's origin is **baked into the APK**
  (`EXPO_PUBLIC_API_URL`), so a handset built for the cloud origin cannot be
  repointed in the room. Either the LAN-origin build is already installed
  (build it Wednesday, keep both APKs) or the handset step becomes
  [Fallback B](#fallback-b--handset-upload-failure-the-debug-delivery-page).
- **the narrator says:** "we are showing this on the upload centre's own
  machine today; the cloud leg is deferred" — and does not claim the cloud leg
  was demonstrated.

**Acceptance gates for the centre-PC variant.** All five, or it is not a
demo-ready fallback:

- [ ] **1. Same revision.** The centre PC runs the same deployed revision as
      the cloud did. There is no SHA on any HTTP route — `/healthz` answers
      `{"ready":true}` and `/api/engineering/status` reports security and
      service state, neither carries a revision — so take it from the checkout
      the server runs from: `git -C <checkout> rev-parse HEAD` on the centre PC,
      and the same on the VM (or the deployed image id). The evidence bundle
      from step 0:33 records the same value, which is how the bundle names the
      code that produced it. The two must match. Rehearsed on ______ by
      ______: PASS / FAIL
- [ ] **2. Card intake passes on it**, with the P0-2 evidence list: real session
      id, source and copy checksums matching, `counter.ts import`, upload,
      verify, review, bill id and amount, then the import and upload retried
      once with **no duplicate episode and no second bill**. Rehearsed on
      ______ by ______: PASS / FAIL
- [ ] **3. Phone upload passes on it** against the LAN origin, with the P0-3
      evidence list: sign in, a distinct real recording uploaded over the demo
      network, `ingested` in that console, income and payout read back from the

- [ ] **4. `demo-preflight.mjs` passes against the centre database** — the same
      command as T-60, with the centre's `DATABASE_URL` and LAN

## Fallback B — handset upload failure: the debug-delivery page

Triggered by: the phone cannot reach the origin, the upload stalls, or the app
crashes.

The console's **Engineering → Debug delivery** page
(`/engineering/debug-delivery`) pushes a session folder from the operator's own
browser through the same delivery code the phone uses. It is available only
where the server reports `PLAYERONE_DEBUG_DELIVERY=1`, and it needs the bucket's
CORS rule for this console origin
(`node packages/api/scripts/bucket-cors.mjs https://<console origin>`) — without
it the page fails with `TypeError: Failed to fetch`, no status and nothing in
the API log, because the request never leaves the browser. Apply the rule and
prove the page **before** Thursday.

**The narrator says:** "the handset could not reach us, so an operator is
pushing the same recording through the same upload path from the console. This
is the platform's own debug tool and it is standing in for the phone." Do not
let it be read as the phone working.

`PLAYERONE_DEBUG_DELIVERY=1` is refused by `deploy/centre/check.mjs` in
`https-production` mode on purpose. On a demo deployment it is a deliberate,
temporary choice; remove it afterwards.

## Fallback C — review blocked: metadata-only review, stated honestly

Triggered by: the queue is empty, or somebody asks the reviewer to play the
video.

There is nothing to switch on. `PLAYERONE_REVIEWER_MEDIA=0` means a reviewer
session receives review metadata and no footage at all, and that is the
deployed, intended state — see the honest line at
[0:19](#019--human-review--reviewer). If the queue is empty, name the reason
from `/episodes` (quarantined ingest, zero measurement, or a `blocks_review`
defect) and review the seeded episode instead. If the room asks to see the
footage, the operator can play it **locally on the centre PC**, where media
never leaves Vietnam — say that is what is happening and why it is not what the
reviewer sees.

## Recovery rehearsal — each one run once, before Thursday

### 1. Database restore from a dump

Row counts before and after, or it proves nothing.

```bash
# before: the dump, and the numbers it should reproduce
pg_dump --format=custom --dbname="$DATABASE_URL" --file=/data/backups/po_demo_$(date +%Y%m%d-%H%M).dump
psql "$DATABASE_URL" -At -c "select 'collectors',count(*) from collectors
  union all select 'tasks',count(*) from tasks
  union all select 'collection_sessions',count(*) from collection_sessions
  union all select 'episodes',count(*) from episodes
  union all select 'episode_reviews',count(*) from episode_reviews
  union all select 'settlements',count(*) from settlements
  union all select 'bills',count(*) from bills
  union all select 'payout_accounts',count(*) from payout_accounts order by 1" | tee /tmp/before.counts

# restore into a SEPARATE database, as its owner. Never restore over the demo
# database to rehearse restoring it.
createdb -U postgres po_demo_restore_test
pg_restore -U postgres --dbname=po_demo_restore_test /data/backups/<the dump>

# after: the same numbers, out of the restored copy
psql "postgres://postgres:...@<host>:5432/po_demo_restore_test" -At -c "<the same query>" | tee /tmp/after.counts
diff /tmp/before.counts /tmp/after.counts && echo "restore verified"
```

`diff` must print nothing. On Windows, `psql -At` output carries `\r`: strip it
(`tr -d '\r'`) before diffing, or the two files never match.

Drop `po_demo_restore_test` afterwards — `CHECKPOINT;` first, then
`DROP DATABASE` (plain, never `WITH (FORCE)`; the refusal while someone is
connected is the guard that stops you deleting a database another agent is
using).

### 2. Certificate re-issue

```bash
cd /srv/playerone/deploy/cloud
docker compose logs caddy | tail -20            # what it says now
docker compose down
docker volume rm playerone_caddy_data           # the certificates live here
docker compose up -d
docker compose logs -f caddy                    # watch the ACME issuance
curl -sSI https://console.<domain>.vn/ | head -1
node deploy/demo-preflight.mjs                  # certificate-expiry reads PASS again
```

Restarting Caddy means restarting the API — they share a network namespace, so
`docker compose restart caddy api`, in that order, or every request answers 502.

**Do this once, deliberately, and not twice.** A fresh issuance on every start
is how a deployment meets Let's Encrypt's rate limit and then has no TLS at
all. Back up `caddy_data` with the database.

### 3. The bucket's lifecycle rule is actually on the bucket

Set by hand, before the first upload, and therefore worth reading back rather
than assuming. Read-only:

```bash
aws s3api get-bucket-lifecycle-configuration \
  --endpoint-url "$STORAGE_ENDPOINT" --bucket "$STORAGE_BUCKET"
```

Expect both rules, `Enabled`: `abort-stale-multipart`
(`AbortIncompleteMultipartUpload`, 7 days, empty prefix = the whole bucket) and
`archive-billed-deliveries` (`Tag tier=archive` → the archive storage class).
See [RUNNING.md](../docs/RUNNING.md) for what each is for and which storage-class
strings HCM04 accepts. `NoSuchLifecycleConfiguration` means no rule is set:
`PutBucketLifecycleConfiguration` replaces the **whole** rule set, so put both
rules in one call and read it back again afterwards.

While you are there, the only way to see orphaned multipart cost:

```bash
aws s3api list-multipart-uploads --endpoint-url "$STORAGE_ENDPOINT" --bucket "$STORAGE_BUCKET"
```

## What must be preserved

- **The demo database** (`po_demo_thursday`, or whatever `po_demo*` name this
  deployment uses). It holds the seeded identities, the reviewed episodes, the
  bill and the declared destination. Dump it after the final rehearsal and
  again after the demo; keep the dump off the VM.
- **`caddy_data`** — the certificates. Losing the volume means a fresh ACME
  issuance on every start, which is how a deployment meets Let's Encrypt's rate
  limit and then has no TLS at all. Back it up with the database.
- **The four demo secrets** (`PLAYERONE_DEMO_MACHINE_SECRET`,
  `_ADMIN_SECRET`, `_FINANCE_SECRET`, `_REVIEWER_SECRET`). The seed compares
  them on a rerun and refuses a different value rather than overwriting a
  sign-in; without them the rerun path is `bootstrap.ts --rotate-operator`.
- **`PLAYERONE_TOKEN_SECRET`.** Rotating it invalidates every session and every
  signed-in browser profile, mid-demo included.
- **The TF card, and the evidence bundle** from step 0:33. The card is never
  written to and never cleared; the bundle is what a stakeholder takes away.
- **The media root** — the imported `ego_*` sessions the review lane reads.

## What must never run against the demo database

Each of these truncates or rewrites, and each is correct against a throwaway
database:

| Never | What it does |
|---|---|
| `packages/api/scripts/seed-console.mjs` | truncates **every** table, then seeds a different console story |
| `packages/api/scripts/e2e-loop.mjs` | truncates every table; it is the loop assertion script |
| `packages/api/scripts/verify-e2e.mjs`, `verify-review.mjs` | assertion scripts; their data exists only for the run |
| `pnpm test` / `vitest` with `DATABASE_URL` pointing here | every database test file truncates, by design |
| `DROP DATABASE` / `WITH (FORCE)` | obvious, and it has happened |
| `PLAYERONE_ALLOW_SUPERUSER=1` with anything but a migration | the application connects as `playerone_app`; that is what keeps the append-only audit triggers honest |

`seed-stakeholder.mjs` and `demo-preflight.mjs` both refuse a database whose
name does not start `po_demo` or `playerone_demo`. That guard protects the
*other* databases from this demo; it does not protect this database from the
scripts above, which have no such guard. The name is the only thing between
them and Thursday — so keep the demo name, and keep every throwaway name
distinct (`po_e2e_*`, `po_test_*`).

Also never, in the room or out of it:

- **Do not flip `PLAYERONE_REVIEWER_MEDIA` to `1`** to make a point. It is a
  separate authorisation, it requires `PLAYERONE_SECURE_COOKIES=1`, and D11 has
  to be answered by Legal first.
- **Do not set `PLAYERONE_PAYOUT_MODE=api`.** With a sandbox environment the
  service refuses to boot at all, and that refusal is deliberate.
- **Do not simulate a payment.** See
  [0:28](#028--the-payment-and-the-honest-ending--finance).
