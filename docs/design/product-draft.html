One design system.
Two very different surfaces.

A web back-office where operators judge footage on a fixed workstation, and an Android app where collectors record it. Same palette, same mascot, same tokens — different jobs, different codebases. Below: the confirmed platform split, the new identity, Cú, and every command to start.

01 — CONFIRMED

Yes. Operator is web, collector is Android.

You asked me to confirm before we go. I checked it against the brief rather than assuming — §3.4 and the architecture diagram both say it outright.

🖥️ Operator — web back-office

Brief §3.4 item 2: "Web back-office — task, collector, device, upload-centre, batch, episode, review and settlement management." Runs on fixed upload-centre machines, needs a machine token and an operator token on every write (PRD §8.3.2 rule 1). Stays on the current stack: TypeScript, Fastify, server-rendered, no build step, works with the link down.

📱 Collector — Android app

Brief §3.4 item 1: "Collector mobile app — Android first, iOS secondary." Decision C10, taken by Alois on 14 Aug. The architecture diagram literally labels the box MOBILE APP (Android). React Native is a sound choice for it.

The part you need to hear before we start on the app. Most of the collector app is blocked, and not by us. D5 — the device SDK and manual — is listed against "Everything" and was promised on 13 Aug. D1 — the Wi-Fi protocol between device and phone — blocks "the entire Path A upload flow". Without them we cannot build device binding (APP-14/15), pre-collection checks (APP-19/22), or any upload.

Buildable today — about 60% of the app

Account and agreements (APP-01/02) · training and exam (APP-03/04/05) · task hall, task detail, claiming, my tasks (APP-08→13) · session declarations (APP-17b) · upload-record screens (APP-23/24) · review results in the collector's language (APP-27) · earnings.

Blocked until PaXini delivers

Device binding · pre-collection battery and storage checks · the recording handoff · Path A upload · firmware display. We can design and stub every one of these, and they stay stubs until D1 and D5 land.

One flag on React Native. Earlier you told me "we can't use React", and I removed a React scaffold from this repo. I read that as a rule for the console — which has no bundler and must run on a LAN with the link down — and not for a native Android app. So: console stays vanilla, the Android app is a separate React Native codebase in its own repo. Say the word if you meant it more broadly.
02 — IDENTITY

A mark that means something, and no gradient blobs

The old mark was a rounded square with a swoosh in it — the thing every generated logo looks like. This one is two circles.

The stereo pair

The Ego headset has two camera lenses side by side. So does the mark. VNG's sun on the left, PaXini's blue on the right, overlapping where the data is. It is also, deliberately, a pair of eyes — which is where Cú comes from.

Holds at 16 px, works in one colour, works on the dark theatre, and survives being an Android launcher icon. No gradient, no bevel, nothing to date it.

03 — MASCOT · D5b

Meet Cú, and the shift she's on

The robot is gone. Cú is Vietnamese for owl — and cú đêm, "night owl", is a real Vietnamese idiom for someone who stays up late. Chinese has the same idiom, 夜猫子. Both partners already have a word for her.

Why an owl, and not a dog or a hedgehog

An owl has two big round forward-facing eyes. So does the Ego headset. The mark, her eyes and the hardware are the same two circles — the identity closes on itself instead of being decoration bolted on. She also does the job: an owl watches, and watching footage is literally the work.

She's driven by the clock, not by a mood picker

Upload centres run shifts and reviewers work nights. Cú reads getHours() and changes with it — four states, no setting, no surprise. An owl forced onto the 6 a.m. shift is funny once a day and never in the way.

Early bird05:00 – 09:00
Day shift09:00 – 17:00
Golden hour17:00 – 22:00
Cú đêm · Night owl22:00 – 05:00

Where she appears

Inside the gauge on both apps, as the empty state, as the loading state, and once when the queue hits zero. Never on the review screen itself — nothing cartoon goes next to footage someone is paid on.

How she's built

Flat SVG, five fills, no gradients on the character. Under 3 KB per state, inline in the console and an react-native-svg component in the app. Same artwork both sides.

What she's worth

She's the thing PaXini remembers after the meeting, and the thing a collector sees every day. That's the entire argument — she does no other work.

Results · APP-23/24/27, reasons in Vietnamese

The reject reason is already localised

Every code in review_reason_codes carries an English, Vietnamese and Chinese label. The operator picks VQ-DARK; the collector reads "Quá tối". That table already exists in the database.

Blocked things stay visibly blocked

The greyed upload row is honest, not broken. It names D1. When the protocol arrives the row lights up and nothing else changes.

Tokens map straight to RN

Every value is a flat token, so theme.ts in the app and shell.ts in the console are generated from the same source. One palette, two runtimes, no drift.

06 — WHAT TO RUN

The commands, in order

You asked which skills to invoke. These are slash commands you type in Claude Code — I can run all of them myself except where noted, so mostly this is you deciding when.

You run these once — they write durable context

Both create files that every later session reads, so they're worth doing deliberately rather than mid-task.

/impeccable init → writes PRODUCT.md: what PlayerOne is, who uses it, platform = adaptive (web + android). Ask me to draft it and you approve — it's the file everything inherits. /impeccable hooks on → runs the design detector after every UI edit and surfaces problems while I'm still in the file.

I run these as I build — no action from you

/impeccable shape <screen> plan before code /impeccable animate scroll + hover motion /impeccable adapt responsive · native variant /impeccable audit a11y, perf, targets /impeccable polish final pass /apple-design HIG review, both surfaces

Impeccable ships audit.native.md and adapt.native.md — real React Native guidance, plus an android.md reference. It knows the platform.

One you may want yourself: /impeccable live opens a browser variant mode where you click an element and get alternatives generated on the spot. That is the fastest way for you to steer the look without describing it in words. Best used once the console is running locally.
07 — BUILD ORDER · D6a

Home + Review + Pipeline, then the app

Each step leaves the console working and all 342 tests green.

  1. Tokens and identity into the shellTwo-brand light system, shadcn naming, the stereo-pair mark, self-hosted fonts, Cú as an SVG module with her four states. Everything downstream inherits it.
  2. App frame — top bar, pill nav, hot switch, routingPlus honest "next" states for Counter, Episodes and Settle so nothing is a dead link.
  3. Review, reskinnedHighest risk, so it goes early. Behaviour untouched; the existing tests are the net.
  4. Home with the gaugeOne new endpoint for shift statistics. Everything else is already in Postgres.
  5. PipelineStatic structure plus live counts. Cheap, and it is what makes the demo tell a story.
  6. Audit pass, then hand you the findingsContrast, hit targets, focus order, keyboard reachability, both themes, EN and ZH.
  7. Then the Android app — separate repoReact Native, same tokens. Start with the 60% that isn't blocked: account, training, exam, task hall, results. Device and upload paths stubbed behind D1/D5.
Chase D1 and D5 now. They gate the collector app's whole reason to exist, one was promised on 13 Aug, and the headset arriving for testing is the natural moment to ask. Everything else here can proceed without them.
