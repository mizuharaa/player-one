# Ego hardware capture — 2026-09-03 (device Ego_AZER76400HV, on-site, one unit)

Live capture against a real Ego over BLE + Wi-Fi from the office laptop. Raw
artifacts alongside this file: gatt.json, provision_log.json, portscan.txt,
port_probe.txt, allow_probe.txt, stream_confirm.txt, telnet_probe.txt.

## BLE pairing + Wi-Fi handoff — WORKS, protocol captured
- Device advertises name `Ego_AZER76400HV`, service `0000ffe0`. GATT: FF01/FF02
  write-only, FF03 read/write/notify (the provisioning channel). Full table in gatt.json.
- Provisioning is exactly the EgoLowBle doc's fixed protocol on FF03:
  `A001` + 32-byte SSID + 32-byte password (0x00 right-padded) -> device replies
  `A001 0 accepted`; `A002` polls -> `A002 2 provisioning` then `A002 0 <ip>`.
  Live run: wrote SSID `iPhone` -> device joined -> reported **172.20.10.2**.
- WinRT gotcha for the Android/desktop client: subscribing to FF03 notifications
  (CCCD write) drops this device's link ("Could not start notify: Unreachable").
  Read-polling FF03 works and is what we should use. The shipped EgoLowBle libs
  may avoid this; our own BLE code must not assume notify.

## Network surface once on Wi-Fi — STREAMING + CONTROL ONLY, no file API
Full TCP scan of 172.20.10.2, open ports: **23, 8090, 8888, 8889, 8890, 8900**.
- 8888/8889/8890: HTTP servers answering `OPTIONS` 200 with
  `Access-Control-Allow-Methods: POST, GET, OPTIONS` and header
  `x-sessioncookie` — the signature of **RTSP-tunneled-over-HTTP media streams**
  (video / audio / IMU). GET returns 405; they are not a file server.
- 8090: the Orbbec SDK control port (`createNetDevice(ip, 8090)`), proprietary,
  no plain-HTTP/RTSP banner.
- 8900: intermittent, no HTTP response.
- 23: **telnet -> Linux login prompt** (`(none) login:` / `Password:`). Not
  brute-forced. If PaXini provides the credentials, the TF card is reachable
  over the network — a possible (undocumented, unsupported) Path A.

## Path A verdict
The documented SDK is streaming-only, and this C++ guide states in its own scope
note (line 12) that it **does not cover record/playback interfaces** — they exist
in the full SDK headers but are not in this kit. So: no documented file-offload
over the network. Two concrete asks for PaXini before Path A can be built:
  1. The **record/playback SDK headers/docs** ("录制/回放") the guide excludes.
  2. Whether the telnet shell (or any service) exposes the recorded files on the
     card, and if so the auth for it.
Until then the pilot stays **Path C only** (card handover at the centre), which
is built and tested.

## Live EgoViewer recording + ingest (added same session)
Ran EgoViewer (v1.0.17) over USB, recorded 26.7 s. It writes a session folder:
left/right H264 MP4, audio WAV, IMU CSV, per-stream PTS sidecars, two calibration
YAMLs, and a rich meta JSON (real duration, status:completed, dropped-frame counts).

**Firmware on the unit is 0.0.13** (SDK 2.9.0), newer than the kit's 0.0.12.

Two format facts that matter for our ingest:
1. **EgoViewer names files `Orbbec_Ego_<serial>_<ts>_camera_left.mp4` (single
   segment, no `_part0001`).** The TF-card/field format is `ego_<serial>_<ts>_
   camera_left_part0001.mp4`. Our `classify.ts` only recognises the card form,
   so an EgoViewer-format folder ingests as **QUARANTINED / MEDIA-MISSING** —
   every file unclassified. If a firmware/SDK change ever alters on-card naming
   toward the EgoViewer form, ingest silently quarantines real data. Worth
   loosening the classifier to accept both prefixes and the no-segment case.
2. Remapped to card naming, the same bytes ingest as **FLAGGED (usable)** on
   firmware 0.0.13: device AZER76400HV, calibration parsed, duration 26.667 s
   measured vs 26.734 declared (manifest advisory, as designed). New flags seen
   on 0.0.13, both real:
   - `FIRMWARE-UNKNOWN: 0.0.13 outside the tested set` — add 0.0.13 to the set.
   - `CAMERA-NAMING-CONFLICT: manifest says color_left/color_right, calibration
     says IR_L/IR_R` — a metadata inconsistency in this firmware's own files.
   (`MANIFEST-FILES-UNRESOLVED` here is a rename artifact of the test, not a device issue.)

**Net:** streaming path proven; ingest proven on current firmware. Still worth a
real TF-card pull to confirm the *card* format on 0.0.13 (segmentation, advisory
manifest) and to capture a true multi-part (>1 h) session, which we still fake.
